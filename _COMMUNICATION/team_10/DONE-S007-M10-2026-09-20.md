**What the fix does:** a one-shot mu-plugin,
`ea-m10-paste-residue-cleanup-once.php`, parses each post's raw `post_content` with
`DOMDocument`, strips `font-family` / `mso-*-font-family` declarations from `style`
attributes, strips `MsoNormal` from `class` attributes, and removes any `<span>` left
with no attributes and no non-whitespace text after that. Nothing else — other CSS
properties genuinely present survive (one post's `<td>` keeps `font-size`/
`text-align`), as do `dir`, `lang`, all text, punctuation, line breaks and links.

**Verified before this ever touched a database**, against saved fixtures of the actual
live content (fetched via the public REST API, `content` in raw form via the plugin
itself at run time): all six posts round-trip with byte-for-byte identical plain text
(whitespace-normalized) before and after, and zero `Arial`/`arial` and zero
`MsoNormal` remain in any of them. One post (193, שיטת השקשוקה) had a **double
HTML-entity-encoded quote** in its style attribute — literal `&amp;quot;` in the
source — which broke a naive semicolon-split on the first attempt (the embedded,
un-decoded `&quot;`'s own semicolon was misread as a declaration separator, so
`font-family:` got dropped but `arial` itself survived attached to the next
fragment). Caught in the dry run before deploying anything, fixed by decoding
entities a second time before splitting, re-verified clean.

**Safety design:**
- Backs up each post's raw `post_content` to `wp-content/uploads/ea-m10-backups/` —
  **before** that post's own write, not after the batch succeeds, so a mid-batch
  failure still leaves already-touched posts individually reversible without a
  database restore.
- Writes via direct `$wpdb->update()`, not `wp_update_post()` — this fires on an
  anonymous front-end request, where `wp_update_post()` would route content through
  `wp_kses_post()` as an unprivileged save with side effects I could not verify
  without a live WordPress request already in progress.
- A hard runtime check re-verifies text-identity for the ACTUAL content it reads at
  execution time (not my pre-fetched snapshot) before writing anything; any post that
  fails that check is skipped and logged, never forced through.
- Idempotent, flag-guarded; a per-post result (byte counts, Arial/MsoNormal
  before-after counts, or the specific skip reason) is recorded to an option.

**Not yet run** — it fires on the first page load after deploy, and this hasn't
deployed. Verification against the live database (post_content diff, rendered-text
diff, confirming the option's own result log) happens after the batched deploy, once
team_00 says go.
