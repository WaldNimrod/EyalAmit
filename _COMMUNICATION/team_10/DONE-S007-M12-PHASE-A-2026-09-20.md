# M-12 Phase A — one shared drawer, native `<dialog>`, every page

## What this is

Per the agreed staging (A complete and shippable on its own, then B): the burger +
open panel of all three mobile menus are now one component — a native
`<dialog>`/`showModal()` drawer, server-rendered once, opened from any element
carrying `data-ea-nav-trigger`. Each page family's own bar/chrome is **untouched** —
Chapters keeps its header, Wave2 keeps `.ea-mnav-controls`, the six orphan pages keep
GeneratePress's own masthead. Only what the burger opens changed.

## Content: the live Chapters list, one item dropped

Used `template-parts/chapters/section-nav.php`'s real tree, not the June package's —
matches what you found diffing both against live REST data. One deliberate drop:
"קורסים" resolves to `href="#"` on the live desktop nav today (already P2-A1 in the
accessibility package). A drawer reaching every page must not carry a dead control
onto pages that never had it.

**What each page family gains or loses, stated plainly, since this is a real content
change and not only a styling one:**

- **The six orphan pages** (`/services/`, `/shows-heritage/`, `/historical-articles/`,
  `/thank-you/`, `/courses-soon/`, `/learning/courses-external/`) go from **no working
  mobile menu at all** to the full Chapters tree — including reach to `/shop/`,
  `/snoring-sleep-apnea/`, and the EN toggle, none of which their desktop header
  (WordPress-menu-driven) can reach either. That gap on desktop is pre-existing and
  unrelated to this mandate — flagging it here only so it's visible, per your
  instruction not to reconcile it myself.
- **Chapters pages** (most of the site): same content as before, same visual bar,
  different underlying mechanism opening it.
- **Wave2 pages** (`/about/`, `/press/`): same. Their own drawer used to carry a
  second, independent copy of the nav tree (`$ea_topnav_items`, still used for the
  desktop dropdown, untouched) — the mobile version of it is gone, replaced by the
  Chapters-sourced shared drawer.

Sound toggle: shown only on Chapters/Wave2 pages, where a real control already exists
(video-mute on Chapters, a visual-only pill on Wave2) — omitted on the six orphans per
your ruling that a control with nothing behind it is worse than no control. EN link:
kept universal, since on every page today it already just points at the one `/en/`
landing, not a per-page translation — showing it on the six orphans adds a real,
working link, not a dead one.

## Verification — real, pre-deploy, and it found two real bugs

Staying under the deploy hold meant no live server yet reflects this code, so
verification ran against a local static-HTML harness carrying the real CSS/JS and the
real design tokens, driven by a dedicated CDP script — real `Input.dispatchKeyEvent`/
`dispatchMouseEvent`, never `.click()`/`.focus()`. Bare-`<dialog>` Escape control ran
first and passed (`windowsVirtualKeyCode:27`), so the method is trusted.

This caught two real defects before either could reach a live page:

1. **The dialog leaked 11 of 15 real Tab stops while "closed."** An unconditional
   `display:flex` on `dialog.ea-nd` overrode the browser's own `dialog:not([open])
   {display:none}` — the exact class of bug this whole mandate exists to eliminate,
   this time from fighting the native default instead of failing to build one. Fixed
   by moving `display` into `dialog.ea-nd[open]` only; re-measured at **0 of 15**.
2. **Every nav row silently overflowed its container on box-sizing:content-box.**
   `ea-atoms.css:46`'s `*{box-sizing:border-box}` doesn't reach the six orphan
   pages — exactly your warning from the last message, borne out in a real
   measurement (`.ea-nd__link` read 408px inside a 335px-wide drawer). Fixed with a
   reset scoped to this component's own subtree, not a global `*`, so it can't touch
   sizing anywhere else on those six pages.

Also confirmed, all via real coordinates/events, none inferred from the DOM alone:
open/close animation states (`translate`, `::backdrop` opacity), accordion
`grid-template-rows` actually expanding on a real click, `body{overflow:hidden}`
during open and released after, the WhatsApp-hide flag firing and releasing,
`elementFromPoint` landing on the dialog even in the ~55px sliver beyond the drawer's
own box at 390px width (native modal inertness covers the full viewport, not just the
visible panel), focus restoring to the burger on close with zero extra code, and every
interactive row at or above 44×44 (burger/close 44×44, leaf link/accordion button
360×52, sublink 360×46).

**Not yet done, and it's the real test:** the same rigor against the actual site —
`/`, `/about/`, `/services/`, `/en/` at 390×844 and 375×667 minimum, per the mandate.
That needs this deployed first. Report follows immediately once it is.
